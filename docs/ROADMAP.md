# Roadmap

## Vision
A mobile workout tracker (eventually on the App Store and Google Play). A user logs a workout for a day: multiple exercises, each with sets of reps and weight. They can edit or delete past workouts and sets, browse their history by week, and see a progress chart for any exercise over time. Being able to change the schema safely as features are added is a priority.

## Phase 2: Edit and delete API (TDD)
- [x] Get one workout, edit a workout, delete a workout, edit or delete a single set (`PATCH`/`DELETE /workouts/:id/sets/:setId`, nested router in `src/routes/sets.ts`).
- [x] Empty workouts are allowed: both `GET /workouts` and `GET /workouts/:id` give `sets: []`.
- [x] `GET /workouts` returns `WorkoutDetail[]` (same shape as `GET /workouts/:id`), newest date first, then id. Two queries in total (workouts, then all their sets via `workout_id = ANY($1)`), not one per workout. Replaced the flat one-row-per-set `WorkoutHistoryRow`.
- [ ] Paginate `GET /workouts`: it returns every workout the user has ever logged. Keyset (cursor) pagination on `(date, id)` fits the existing order, e.g. `?before_date=&before_id=&limit=`, and stays correct when workouts are added between pages (unlike `OFFSET`). Do it alongside the history-by-week screen, which may want a date range (`?from=&to=`) instead.
- [x] `POST /workouts/:id/sets` adds one set to an existing workout (including an emptied one) and returns 201 with the full `WorkoutDetail`. The set becomes the last of its exercise (see `set_number` below).
- [x] Set values the columns can't store are a 400, not a 500 or a silent round: weight must fit `NUMERIC(6,2)` (≤ 9999.99, at most 2 decimals), and `reps`, `exercise_id` must fit `INTEGER` (≤ 2147483647). Applies to `POST /workouts`, `POST .../sets` and `PATCH .../sets/:setId`.
- [x] `set_number` is a set's position within its exercise in a workout: 1..n per exercise, no gaps or duplicates (Squat 1-3, Bench 1-2). Settled before Templates, where "set 2 of Squat" (and prefill from last time) needs one meaning.
  - The server owns it. `POST /workouts` numbers each exercise's sets in the order they're sent; `POST .../sets` uses that exercise's highest + 1; `DELETE .../sets/:setId` moves the exercise's later sets down one. A client-sent `set_number` is a 400 in both POSTs, which (like `POST .../sets` already did) now reject any unknown key in a set. `PATCH .../sets/:setId` only takes `reps`, `weight`, `unit`: a set's exercise and number can't change (delete it and add it under the right exercise).
  - Migration `per-exercise-set-numbers` renumbered existing sets by their old `(set_number, id)` order, so nothing moved, and added `UNIQUE (workout_id, exercise_id, set_number) DEFERRABLE INITIALLY IMMEDIATE`. Deferrable because Postgres checks a plain unique constraint after each row, so the "move later sets down one" `UPDATE` could fail halfway. Tested in `test/migrations/` against a scratch schema migrated to just before it, with old-style rows.
  - Concurrency: adding a set, deleting one, and removing an exercise each run in a transaction (`withTransaction`, `src/db/transaction.ts`) that first locks the workout row (`lockWorkout`, `SELECT ... FOR UPDATE`, `src/db/workoutLock.ts`), so writes to one workout's numbers run one at a time. The constraint alone would catch duplicates but not gaps (an add reading the highest number just before a delete shifts it). Tests fire such requests at once; a race can pass by luck, so they guard the lock rather than prove it.
  - `GET /workouts` and `GET /workouts/:id` return sets grouped by exercise, each by `set_number`, with the exercises in their stored order (below).
- [x] Exercise order in a workout is stored: migration `workout-exercises` adds `workout_exercises (workout_id, exercise_id, position)`, backfilled in the old order. Bug it fixes: exercises were ordered by their oldest surviving set (`MIN(id)`), so deleting an exercise's first set could move its whole card below exercises added before its second set (e.g. Squat logged, Bench added, then "+ Add set" on Squat). On the phone it looked like the exercise's other sets had been deleted. Regression test: "keeps the exercise's place in the workout when its first set is deleted".
  - Every set's `(workout_id, exercise_id)` must be a `workout_exercises` row (composite FK `sets_workout_exercise_fkey`, `ON DELETE CASCADE`). An exercise's row is added with its first set (`POST /workouts` in list order; `POST .../sets` after the workout's other exercises) and removed with its last (`DELETE .../sets/:setId`), so an exercise that comes back goes to the end. "Remove exercise" deletes the row, which deletes its sets. Positions may have gaps; they're only compared. Helpers in `src/db/workoutExercises.ts`; the same visibility trigger as `sets` runs on the table.
  - Templates can reuse the position, e.g. to reorder exercises (a `PATCH` that swaps positions would need the unique `(workout_id, position)` made `DEFERRABLE`, like `set_number`'s).
  - Not explained by this: whether sets were also really deleted. The server deletes one set per request and the app sends one DELETE per confirmed tap, but the backend doesn't log requests, so a phone session can't be checked afterwards.
- [ ] Signup: no email format or minimum password length check.
- [ ] The seeded test user (`test@example.com`, `src/db/seed.ts`) has `password_hash` set to the literal string `'placeholder'`, not a bcrypt hash, so no password logs it in (`bcrypt.compare` against a non-hash is always false). Seed a real hash (e.g. `bcrypt.hash` of a documented dev password, only when not in production) or drop the user and sign up in the app. Since the insert is `ON CONFLICT DO NOTHING`, existing databases keep the placeholder until the row is updated or deleted.
- [x] `GET /exercises` requires a token and returns the built-in exercises (`created_by IS NULL`) plus the caller's own custom ones, never another user's. `requireAuth` now runs on the whole exercises router.
- [x] `POST /exercises` creates a custom exercise for the caller: `{ name, muscle_group? }`, both trimmed (a blank muscle group is `null`). 400 for a missing or blank name, a name over 100 characters or a muscle group over 50 (counted in code points, as `VARCHAR` does, so 100 emoji fit), or an unknown key. 409 if the caller can already see that name, ignoring case: their own or a built-in one (one `INSERT ... WHERE NOT EXISTS`, plus 23505 for a race). 201 with the `Exercise`. Tests in `test/exercises.test.ts`.
  - Migration `custom-exercises`: the unique index is now `(created_by, lower(name))`, and a `BEFORE INSERT OR UPDATE` trigger on `sets` (`sets_exercise_visible`) rejects an exercise that's neither built-in nor the workout owner's. Before it, `POST /workouts`, `POST /workouts/:id/sets` and `PATCH .../sets/:setId` accepted another user's custom exercise by id (the FK only checks it exists). The trigger raises 23503, so those routes return the same 400 `Unknown exercise_id` as a missing exercise, and 404s for another user's workout or set still come first. Progress and `GET /exercises/logged` already filtered by visibility.
- [ ] Edit and delete custom exercises (e.g. `PATCH`/`DELETE /exercises/:id`, own ones only, same name rules as `POST`). Deleting one that has sets needs a decision: refuse (409), delete its sets too, or hide it (soft delete) so past workouts keep their names.
- [x] `DELETE /workouts/:id/exercises/:exerciseId` removes all of one exercise's sets from a workout in one statement and returns 200 with the updated `WorkoutDetail` (router `src/routes/workoutExercises.ts`). 404 `Workout not found` for a missing or another user's workout, 404 `Exercise not in this workout` when it has no sets of that exercise.
- [x] Split routes out of `app.ts` into `express.Router` files in `src/routes/` (auth, workouts, exercises, health). `requireAuth` runs on the whole workouts router.

## Phase 4: Progress charts
- [x] Weight as a number: a pg type parser for NUMERIC (OID 1700) in `db/pool.ts` returns `Number(value)` (exact for `NUMERIC(6,2)`), and `WorkoutSet.weight` is a `number` (e.g. `135`, `132.5`; no trailing zeros). The mobile response guard requires a finite, non-negative number and rejects the old string form; `formatWeight` was removed. The parser is global, so future `SUM`/`AVG` over weight also come back as numbers (exact up to ~15 significant digits).
- [x] DATE time zone (done early, in Phase 3, since week grouping needs the right day): a pg type parser for DATE (OID 1082) in `db/pool.ts` returns `'YYYY-MM-DD'`, and `Workout.date` is a `string`. Tests assert exact dates where they set one and the `YYYY-MM-DD` format elsewhere.
- [ ] `POST /workouts` without a `date` falls back to `new Date()`, i.e. "today" in the server's time zone, which may not be the user's day. The app always sends a date, so it's harmless for now; consider making `date` required.
- [x] `GET /exercises/:id/progress?unit=&from=&to=` (requires auth): one point per workout date, oldest first, each with `top_weight`, `e1rm`, `volume` and `sets`, all from the caller's own sets.
  - Every set is converted to `unit` before aggregating (1 lb = 0.45359237 kg exactly), and results are rounded to 1 decimal. `unit` is optional: when missing, the server uses the unit of the caller's most recent set of that exercise (`lb` if none), and the response always says which unit it used.
  - `e1rm` is Epley, `weight × (1 + reps/30)` (a 1-rep set is its weight), on every set with 1+ reps, no cap. Only sets with 1+ reps count, for every metric and for the default unit: a 0-rep set (failed attempt, the 0×0 placeholder) adds nothing to volume and mustn't be the heaviest set. A day with only 0-rep sets has no point.
  - `from`/`to` optional and inclusive (all time when missing). 400 for a bad date, `from > to` or an unknown unit; 404 for an exercise that's neither built-in nor the caller's; `points: []` for one never logged.
- [x] `GET /exercises/logged` (requires auth): the exercises the caller has logged a set of 1+ reps for (built-in or their own), most recent first, then by name, with `last_date` and `unit` (the unit of the most recent set), for the progress picker. SQL for both in `src/db/progress.ts`; tests in `test/progress.test.ts`.
- [x] Progress screens (stack screens; tabs wait for Phase 5): `/progress` lists logged exercises with search, opened from a History header button; `/progress/[exerciseId]` shows the chart, also opened from "View progress" in the workout detail's exercise card menu. Toggle between estimated 1RM (default), heaviest set and volume; range presets 3M / 6M (default) / 1Y / All. Bodyweight-only exercises show "no weighted sets". Chart: Victory Native (Skia, in Expo Go).
  - Also an lb/kg switch (starts on the server's default unit), Latest/Best tiles, press-and-hold readout, and a list of every point under the chart (newest first), which is what screen readers and tests read. Series color is the theme's `chart` token (blue; black/white read as gray next to the axes).
  - The chart lives only in `components/progress-chart.tsx`; `jest.setup.tsx` replaces it with a placeholder in every test, since Skia can't render in Jest. Check chart changes on a phone.
  - Root layout is wrapped in `GestureHandlerRootView` (needed for the chart's press gesture).

## Phase 5: Templates
- [x] Migration `templates`: `templates (id, user_id, name)` with a unique index on `(user_id, lower(name))`, and `template_exercises (template_id, exercise_id, position, set_count)`, shaped like `workout_exercises` (primary key on the pair, unique `(template_id, position)`, `ON DELETE CASCADE` from the template). `set_count` is 1 to 20. No target reps or weight: starting a workout prefills them from the last time each exercise was logged. Workouts aren't linked to templates (no `workouts.template_id`), so editing or deleting a template never changes a past workout.
  - Trigger `template_exercises_exercise_visible`: the sets visibility rule for templates (built-in or the template owner's own exercise), raising 23503 so routes can return the usual 400. Without it, reading a template back would show another user's custom exercise name.
  - Positions aren't `DEFERRABLE`: editing a template will replace all its rows in one locked transaction rather than swap positions.
  - The exercise FK has no cascade, so deleting a custom exercise used by a template is a 23503: one more case for the "edit and delete custom exercises" decision above.
  - Tests in `test/migrations/templates.test.ts`.
- [ ] Save a reusable workout (e.g. "leg day") as a list of exercises.
- [ ] Start a new workout from a template so only the numbers need filling in.

## Known issues
- **Intermittent Vitest worker crash on Windows.** About 7% of `npm test` runs (6 of 90 measured, 2026-10-08) end with `Worker exited unexpectedly with exit code 3221226505` (`0xC0000409`, a native fast-fail), always while running `test/workouts.test.ts`. The rest of the suite passes; rerunning gets a clean run. Seen on the untouched tree too, so it isn't caused by a specific change. Node 24.15, Vitest 5.0.3, `pool: 'forks'` (default).
  - 2026-10-16, after the per-exercise `set_number` change: 4 of 20 runs of `test/workouts.test.ts` alone crashed, each early in the file (after 5 to 39 tests, before the new concurrent-request tests run), with no assertion failures in any run. Not compared against a baseline of that file alone, so it's unclear whether the rate changed.
  - Ruled out: `pool: 'threads'` (same rate, ~4 in 60, and worse: the whole Vitest process dies with no summary, so failures are silent); swapping `bcrypt` for `bcryptjs` (crashed 2 of the first 7 runs with no native bcrypt loaded).
  - Not yet tried: `isolate: false`, `pg` native bindings (not used, but worth confirming), a different Node 24 patch or Node 22, splitting `workouts.test.ts` (largest file) to see if size or run time matters.

- **Typed routes go wrong when a file is added while Expo runs (Windows).** Expo's route-type watcher checks `path.relative(...).startsWith('../')`, but Windows paths use `..\`, so files outside `src/app` get added as routes and new route files get backslashed keys (seen 2026-10-14, Expo SDK 57, `@expo/router-server`). `npm run typecheck` then rejects valid routes like `/progress`. Fix: restart `npx expo start`, which regenerates `.expo/types/router.d.ts` from scratch.

  - Once real users run older app versions (store updates roll out slowly, and some people never update), breaking API changes need a transition period or API versioning. A breaking change is any change an older app's response guards reject, like Phase 4's switch of `weight` from `"135.00"` to `135`. Either support both forms for a while (add the new form first, ship the app, remove the old form later), or version the API (e.g. `/v2/...`, or a version header the app sends).
